# Chrome Bookmarks Manager V0.5 Editing Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: use the Superpowers subagent-driven development workflow. Execute one task at a time with RED → GREEN → REFACTOR evidence, focused commits, and an independent spec/code review before advancing.

**Goal:** Add safe in-memory bookmark editing to the completed V0.4 browser/search application: add bookmark, add folder, rename bookmark/folder, edit URL, and explicit dirty-state tracking, while keeping production Chrome `Bookmarks` write-back completely disabled until V0.9.

**Architecture:** Evolve the V0.2 domain model from immutable-facing/read-only data into controlled mutable state without exposing arbitrary JSON mutation. Editing is performed only through application/domain services. Public collection surfaces remain read-only; mutation helpers stay internal. New Chrome-compatible node identity follows current Chromium behavior: IDs advance from the decoded maximum ID, UUIDs are random v4 values, and new-node timestamps use Chrome's Windows-epoch microsecond format. After every successful edit, UI/browser/search projections are refreshed from the same original domain graph and the document enters `LoadedDirty`. V0.5 never serializes, saves, replaces, backs up, or writes the source file.

## Chromium compatibility evidence used by V0.5

Current Chromium bookmark model/codec behavior was rechecked before implementation:

- `BookmarkModel::AddFolder()` and `AddURL()` allocate a node ID with `generate_next_node_id()`.
- `generate_next_node_id()` returns `next_node_id_++`.
- The codec reports the next node ID as decoded maximum ID + 1.
- New folders/URLs use a random v4 UUID when one is not supplied.
- New folder/URL creation uses the current time for creation; folders also receive a current modified time.
- The codec persists bookmark times as microseconds since the Windows epoch.
- URL addition in Chromium requires a valid `GURL`; V0.5 must not normalize or rewrite URL text merely for display convenience.

This project still defers the final Chrome persistence/round-trip gate to V0.9.

## Global Constraints

- V0.5 editing is **in memory only**.
- Do not add any production writer, serializer-to-disk, Save command, overwrite, backup, checksum generation, atomic replace, Chrome-process overwrite path, or profile write-back.
- The source Chrome `Bookmarks` file must remain byte-for-byte untouched during V0.5 owner acceptance.
- UI must not mutate JSON or domain objects directly.
- All edits must flow through a dedicated editing service/contract.
- Public folder child collections remain read-only-facing.
- Permanent roots (`bookmark_bar`, `other`, `synced`) may contain new children but cannot themselves be renamed, URL-edited, removed, moved, or replaced.
- Existing nodes retain their ID, GUID, metadata, unknown fields, and raw timestamps when renamed or URL-edited.
- Newly created IDs must be unique positive decimal strings and advance from the decoded maximum.
- Newly created GUIDs must be non-empty unique v4 GUIDs.
- New timestamp generation must be isolated behind a Chrome-time component and must not use culture-specific formatting.
- Editing must not clone the full ~119 MB document.
- Search must reflect renamed URLs/names and newly added bookmarks without rereading the source file.
- Dirty state begins only after a successful mutation.
- Failed/no-op mutations must not mark the document dirty.
- Loading a new document resets dirty state.
- V0.5 UI must clearly state that changes are not persisted yet.
- Closing/replacing a dirty in-memory document must require an explicit discard/cancel decision; there is no fake Save path in V0.5.
- No private bookmark titles, URLs, queries, raw file contents, or screenshots may be committed or uploaded.
- No new NuGet dependency is permitted unless separately justified and reviewed.

## V0.5 Editing UX Contract

After a document loads:

1. the selected ordinary folder can receive a new bookmark or new subfolder;
2. permanent roots can receive children but cannot themselves be renamed;
3. an ordinary selected folder can be renamed;
4. a selected bookmark can be renamed;
5. a selected bookmark URL can be edited;
6. a successful edit immediately updates the visible browser/search projections;
7. the document state changes from `LoadedClean` to `LoadedDirty`;
8. the status area indicates unsaved in-memory changes and that disk save is not yet available;
9. clearing/re-entering search sees the updated in-memory data;
10. opening another file or closing the app while dirty requires discard/cancel confirmation;
11. V0.5 never writes the real source file.
