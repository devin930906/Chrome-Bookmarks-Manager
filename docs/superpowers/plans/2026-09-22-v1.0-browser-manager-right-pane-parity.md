# V1.0 Browser-Manager Right-Pane Parity Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Upgrade the right-hand content pane from bookmark-only rendering into a Chrome-style mixed folder/bookmark manager so a selected folder exposes and manages its direct child folders and bookmarks from the same pane.

**Architecture:** Preserve `BookmarkNode` / `BookmarkFolder.Children` as the single source of truth and preserve the exact mixed child order stored in the document. Add a thin `BookmarkListItemViewModel` projection for right-pane rendering and selection, keep `SelectedFolder` as the current navigation folder, and add a separate right-pane content selection so selecting a child folder does not accidentally rename/delete the parent folder. Reuse the existing edit, move, delete, history, search, and Safe Save services; add generic mixed-node relative move entry points only where the existing bookmark-only / folder-only UI assumptions prevent Chrome-style right-pane Drag & Drop.

**Tech Stack:** C# / .NET 10 / WPF / XAML / xUnit / PowerShell 7 / Node.js UI contract scripts / GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-09-21-v1.0-stable-release-design.md`

## Global Constraints

- Product goal is browser bookmark-manager functional parity for core local bookmark management.
- The selected folder's right pane must display both direct child folders and direct bookmark URLs.
- Preserve the exact `BookmarkFolder.Children` mixed order; do not silently group all folders or all URLs unless a separately selected sort operation explicitly does so.
- Right-pane folder selection is not the same concept as the current navigation folder.
- Permanent Chrome roots remain protected from rename, move, and delete.
- Search results remain bookmark-result views unless a separately specified folder-search feature is implemented.
- Right-pane folder operations and left-tree folder operations must mutate the same domain objects and history.
- Existing bookmark multi-selection remains supported.
- Chrome-style folder selection is single-item; mixed folder+bookmark multi-selection is normalized to a single folder or bookmark-only set rather than inventing unsupported batch-folder semantics.
- Explicit Save, Chrome-running blocking, source-baseline conflict detection, verified backup, atomic replacement, checksum regeneration, and post-write validation remain unchanged.
- No new NuGet dependency.
- Every behavior change follows RED -> GREEN -> REFACTOR.
- The pre-parity V1.0 RC is not eligible for final owner acceptance, merge, tag, or release.

## Review Focus

1. **Parent vs child folder confusion:** selecting a folder row in the right pane must never cause rename/delete/move commands to operate on the currently open parent folder.
2. **Mixed-order corruption:** moving a folder relative to a bookmark, or a bookmark relative to a folder, must preserve the exact resulting `BookmarkFolder.Children` sequence and Undo/Redo must restore it exactly.
3. **Search leakage:** activating search must not expose folder rows as fake bookmark results or permit positional Drag & Drop against filtered search output.
4. **Protected roots / descendant cycles:** right-pane Drag & Drop must still reject permanent-root moves and moving a folder into itself or its descendant.
5. **Selection regressions:** bookmark Ctrl/Shift multi-selection and existing batch move/delete must keep working after the ListView switches from `BookmarkUrl` rows to mixed item wrappers.

{
    public BookmarkListItemViewModel(BookmarkNode node)
