---

## 1. Purpose

V0.6 adds browser-like bookmark movement to the existing offline Windows application.

The product goal is to let the owner manage Chrome bookmarks from this standalone program instead of opening Chrome's bookmark manager for routine organization work.

V0.6 must support both:

1. direct mouse drag-and-drop, and
2. an explicit **Move to...** dialog.

Both movement entry points must use the same application-level move engine.

V0.6 remains in-memory only. It must not write to the source Chrome `Bookmarks` file.

---

## 2. User-visible scope

### 2.1 Bookmark movement

A bookmark can:

- move up or down relative to other bookmarks in its current folder;
- move to another folder;
- be dropped before or after another bookmark when the drop target exposes an exact position;
- be dropped onto a folder, which moves it into that folder;
- be moved through **Move to...**, which places it at the end of the chosen target folder.

### 2.2 Folder movement

A folder can:

- move up or down relative to sibling folders under the same parent;
- move into another folder;
- move across branches of the folder tree;
- be moved through **Move to...**, which places it at the end of the chosen target folder.

Moving a folder moves the same folder object and its complete descendant subtree. The folder is not copied or reconstructed.

### 2.3 Two movement entry points

#### Drag & Drop

Used for fast, positional movement.

Supported interaction paths:

- bookmark row -> bookmark row: reorder before/after;
- bookmark row -> folder tree item: move into that folder;
- folder tree item -> sibling folder position: reorder;
- folder tree item -> another folder: move into that folder.

Drag/drop may expose **Before**, **After**, or **Into** according to the target.

#### Move to...

Available from the context menu for a movable bookmark or folder.

The dialog:

- shows the three Chrome roots and their descendant folders;
- allows choosing a valid target folder;
- disables or excludes illegal destinations;
- moves the node to the end of the selected target folder;
- does not ask for an insertion index.

## 3. Existing UI remains intact

V0.6 keeps the current V0.5 layout:

- left: folder tree;
- right: bookmark list;
- search box and search scope controls;
- status bar;
- existing add / rename / edit-URL commands.

V0.6 does not redesign the application into a combined folder-and-bookmark list.

Folder ordering is manipulated through the left folder tree.

Bookmark ordering is manipulated through the right bookmark list.

Cross-folder movement is available from both drag/drop and **Move to...**.

## 4. Architecture

Movement is a separate application concern rather than another branch of WPF event code.

Add:

```text
Application/
└─ Moving/
   ├─ IBookmarkMoveService.cs
   ├─ BookmarkMoveService.cs
   ├─ BookmarkMoveError.cs
   ├─ BookmarkMoveException.cs
   └─ BookmarkMoveResult.cs
```

The WPF layer never mutates `BookmarkFolder.Children` directly.

The ViewModel never performs detach/insert logic directly.

All movement goes through one application service.

Conceptual core operation:

```text
MoveNode(
    document,
    node,
    targetParent,
    targetIndex)
```

The same primitive powers:

- same-folder reorder;
- cross-folder bookmark movement;
- cross-folder folder movement;
- drag/drop;
- Move to...;
- future V0.7 batch move composition;
- future V0.8 undo/redo.

## 5. Domain mutation primitives

`BookmarkFolder` currently owns a private mutable child list and exposes a read-only view. Preserve that encapsulation.

Add focused internal primitives such as:

- `IndexOfChild(BookmarkNode node)`;
- `RemoveChildAt(int index)`;
- `InsertChild(int index, BookmarkNode child)`.

The public surface remains read-only.

The domain layer must enforce:

- a child cannot be inserted while it still belongs to a different parent;
- insert indexes must be valid;
- removal clears the removed node's `Parent`;
- insertion assigns the new `Parent`;
- the same node cannot appear twice in one child list.

The application move service coordinates detach and insert so that failure cannot leave a node attached to two parents.

---

## 6. Move invariants

Every move must satisfy all of the following.

### 6.1 Protected roots

The permanent Chrome roots are never movable:

- `bookmark_bar`;
- `other`;
- `synced`.

They remain valid destination folders.

### 6.2 Membership

The moved node and destination folder must belong to the active `BookmarkDocument`.

### 6.3 Cycle prevention

A folder cannot move:

- into itself;
- into any descendant folder.

Cycle validation occurs in the application service, not only in the UI.

### 6.4 Single-parent ownership

After a successful move:

- the node exists exactly once;
- the old parent no longer contains it;
- the new parent contains it exactly once;
- `node.Parent` equals the new parent.

### 6.5 Identity preservation

Moving does not regenerate:

- node ID;
- GUID;
- timestamps;
- extension data;
- metadata;
- URL;
- descendants.

A move changes hierarchy/order only.

### 6.6 Counts

`BookmarkDocument.UrlCount`, `FolderCount`, and `TotalNodeCount` do not change after a move.

### 6.7 No-op moves

Dropping a node into its current effective position is a no-op:

- no duplicate mutation;
- no dirty-state transition if the document was clean;
- no unnecessary search-index rebuild.

## 7. Index semantics

The underlying Chrome folder stores one ordered mixed `children` sequence containing both folders and URLs.

The current UI presents folders and bookmarks separately.

V0.6 must preserve the real mixed sequence while providing intuitive separate-view reordering.

### 7.1 Bookmark reorder in the right list

When the user reorders bookmarks inside one folder, bookmark ordering changes relative to other bookmarks while folder slots remain stable.

Example real sequence:

```text
Folder-A, Bookmark-1, Folder-B, Bookmark-2
```

Right-side bookmark view:

```text
Bookmark-1
Bookmark-2
```

Dragging `Bookmark-2` before `Bookmark-1` produces:

```text
Folder-A, Bookmark-2, Folder-B, Bookmark-1
```

This preserves folder placement while changing bookmark order.

### 7.2 Folder reorder in the tree

The equivalent rule applies to sibling folders: folder order changes relative to other folders while bookmark slots remain stable.

### 7.3 Exact positional cross-folder drop

When dropping before/after an explicit node target, calculate the corresponding real mixed-child insertion index from that target.

### 7.4 Move to... append

The dialog always inserts at the real end of the selected target folder's children.

## 8. Drag & Drop behavior

### 8.1 Drag threshold

Do not start a drag on normal click. Start only after the pointer exceeds the standard system drag threshold.

### 8.2 Valid drag sources

- movable folder tree item;
- bookmark list row.

The three permanent roots are not valid drag sources.

### 8.3 Valid drop targets

Folder tree items can accept:

- bookmarks: Into;
- folders: Into, Before, After where meaningful.

Bookmark list rows can accept bookmarks:

- Before;
- After.

A bookmark is never a container target.

### 8.4 Search results

Search-result rows may be moved to another folder through **Move to...** and may be dragged onto a folder.

Positional bookmark reorder is disabled while search mode is active because the result list is not a direct representation of one folder's ordering.

After a search-result move, the search result remains coherent with the same node reference and current search query/scope.

### 8.5 Visual feedback

Use clear but minimal WPF feedback:

- valid folder target highlight for Into;
- insertion indicator for Before / After;
- prohibited cursor/state for invalid targets.

Auto-expand-on-hover is not required for V0.6's release gate. It may be added later if it can be implemented without destabilizing virtualization or drop targeting.

## 9. Move to... dialog

Add a focused WPF dialog, for example:

```text
MoveNodeDialog.xaml
MoveNodeDialog.xaml.cs
```

The dialog receives:

- active document folder roots;
- node being moved;
- validity predicate / disabled-target state.

It returns one selected target `BookmarkFolder`.

Behavior:

- root folders are visible and selectable as destinations;
- the moved folder itself is disabled;
- descendants of a moved folder are disabled;
- initial selection should be the current parent when practical;
- OK is enabled only for a valid destination;
- Cancel makes no change.

The dialog does not own domain mutation.

---

## 10. ViewModel integration

Add explicit capability state such as:

- `CanMoveSelectedBookmark`;
- `CanMoveSelectedFolder`;
- movement methods that accept target folder / target position.

The ViewModel is responsible for orchestration:

1. validate loaded/editable state;
2. call `IBookmarkMoveService`;
3. if the move changed data, mark document dirty;
4. refresh browser projections;
5. preserve or restore a sensible selection;
6. refresh search state/index only as required;
7. update status text.

The ViewModel must not manually remove/insert nodes.

---

## 11. Projection refresh

V0.5 rebuilds projections after edits. V0.6 must keep folder tree, current bookmark list, and search coherent after movement.

Required outcomes:

- moved folder appears under its new parent;
- old parent no longer shows the moved folder;
- folder reorder is visible immediately;
- bookmark reorder is visible immediately;
- moving the selected bookmark keeps a useful selection when possible;
- moving the currently selected folder keeps it selected when possible;
- current-folder search scope reflects the selected folder's post-move contents;
- global search continues to reference the original bookmark objects.

A full search-index rebuild is acceptable for correctness at first, but implementation should avoid it for a pure move if the index stores node references and does not encode hierarchy-sensitive fields. Current-folder scope must still derive from the updated parents.

---

## 12. Dirty-state behavior

A successful non-no-op move transitions:

```text
LoadedClean -> LoadedDirty
```

A move while already dirty remains dirty.

Canceled, invalid, or no-op movement does not change state.

V0.6 still has no Save command and no production write-back.

Closing or loading another file while dirty continues to use the existing V0.5 discard confirmation.

---

## 13. Error model

Use movement-specific errors, for example:

- `ProtectedRoot`;
- `NodeNotInDocument`;
- `TargetNotInDocument`;
- `SelfTarget`;
- `DescendantTarget`;
- `InvalidIndex`;
- `InvalidDropTarget`.

UI converts these into a user-readable warning without exposing stack traces.

---

## 14. Performance and scale

The real owner dataset is approximately 209k URLs and 3.4k folders.

A move must mutate only the affected parent child lists and necessary projections. It must not clone the entire document.

Add synthetic movement-scale coverage for large folders / many folders.

The release gate should include a representative large generated document and confirm:

- no full-document clone;
- node counts unchanged;
- hierarchy remains valid;
- move/reorder completes within a practical interactive range on CI/owner hardware.

No artificial timing promise is encoded into correctness tests.

## 16. Privacy and safety

V0.6 CI uses only synthetic/anonymized data.

Never commit:

- the owner's real `Bookmarks` file;
- private titles;
- private URLs;
- screenshots containing private bookmark data;
- raw real-file dumps.

V0.6 must not write, overwrite, rename, replace, or back up the source Chrome file.

Direct Chrome persistence remains deferred to V0.9.

---

## 17. Out of scope

V0.6 intentionally excludes:

- delete;
- multi-selection;
- batch move;
- batch delete;
- Undo / Redo;
- Save / Save As;
- Chrome checksum generation;
- Chrome process detection;
- production write-back;
- import/export;
- copy/duplicate;
- automatic folder-hover expansion as a release requirement.

Those remain assigned to later milestones unless a prerequisite strictly requires a small seam now.

V0.6 is complete only when all of the following are true:

- bookmark same-folder reorder works;
- bookmark cross-folder drag/drop works;
- bookmark **Move to...** works;
- folder same-parent reorder works;
- folder cross-folder drag/drop works;
- folder **Move to...** works;
- protected roots cannot move;
- folder cycles are impossible;
- IDs/GUIDs and node objects are preserved;
- document counts are unchanged by moves;
- tree/list/search projections remain coherent;
- successful moves set dirty state;
- no-op/cancel/invalid moves do not falsely dirty;
- source Chrome file remains byte-for-byte untouched during owner acceptance;
- full automated test suite passes;
- Windows single-EXE publish/smoke gates pass;
- Windows 10 owner acceptance passes.

---

## 19. Product-intent rule for future work

Chrome Bookmarks Manager is intended to become a standalone offline alternative to opening the browser's built-in bookmark manager for normal bookmark-management work.

When future implementation choices are ambiguous, prefer behavior that:

1. matches familiar browser/bookmark-manager expectations;
2. preserves Chrome data integrity;
3. remains efficient on the owner's large bookmark library;
4. keeps direct Chrome write-back disabled until V0.9 safety gates are complete.
