# Chrome Bookmarks Manager V0.7 — Delete / Batch Design

> **Repository:** `devin930906/Chrome-Bookmarks-Manager`  
> **Branch:** `feature/v0.7-delete-batch`  
> **Status:** PRODUCT INTENT LOCKED / TECHNICAL IMPLEMENTATION PLANNED  
> **Date:** 2026-09-20  
> **Baseline:** V0.6 completed on `main` at `caddccc40228a40680a310e4871d80298459ac48`

---

## 1. Purpose

V0.7 adds browser-manager-style deletion and multi-selection workflows on top of the completed V0.6 move/reorder feature set.

The product goal remains the same: routine Chrome bookmark organization should be possible from the standalone Windows application without opening Chrome's bookmark manager.

V0.7 introduces destructive **in-memory** operations, but it still does not save or write anything to the source Chrome `Bookmarks` file.

---

## 2. User-visible scope

### 2.1 Single bookmark delete

A selected bookmark can be deleted from the active in-memory document.

Entry points:

- bookmark context menu -> **Delete**;
- Delete key while the bookmark list owns focus.

Deletion requires explicit confirmation.

### 2.2 Single folder delete

A normal folder can be deleted from the folder tree.

Deleting a folder removes the folder and its complete descendant subtree from the in-memory document.

Permanent Chrome roots remain protected and cannot be deleted:

- `bookmark_bar`;
- `other`;
- `synced`.

Folder deletion requires explicit confirmation and the confirmation must make clear that descendants are included.

### 2.3 Bookmark multi-selection

The right-side bookmark list changes from single-selection behavior to WPF extended selection:

- click -> one item;
- Ctrl+click -> add/remove individual bookmarks;
- Shift+click -> range selection;
- Ctrl+A while the bookmark list owns focus -> select all displayed bookmark rows.

The folder tree remains single-select in V0.7. Multi-selecting folders is intentionally out of scope because WPF TreeView has no native browser-like multi-selection model and adding a custom tree-selection subsystem would increase risk without being required for the current milestone.

### 2.4 Batch delete bookmarks

Two or more selected bookmark rows may be deleted in one confirmed operation.

Batch deletion may operate on:

- current-folder bookmark rows;
- active search-result rows.

Selected search results may originate from different folders. The operation works on the underlying bookmark object references rather than display copies.

### 2.5 Batch Move to...

V0.7 composes the V0.6 movement engine into a batch operation.

Multiple selected bookmarks may be moved through **Move to...** to one destination folder.

Rules:

- all selected bookmarks are validated before mutation;
- the destination is one valid folder;
- selected bookmarks are appended to the destination end as one ordered group;
- the group order follows the current displayed-list order captured before mutation;
- duplicate references are rejected/normalized before mutation;
- a failure must not intentionally leave a half-applied batch.

This completes the V0.6 design's deferred batch-move composition.

## 3. Existing layout remains intact

V0.7 keeps:

- left folder tree;
- right bookmark list;
- search box and scope controls;
- status bar;
- V0.5 editing commands;
- V0.6 Drag & Drop and Move to....

The application is not redesigned into a combined folder/bookmark table.

## 4. Architecture

Deletion becomes a separate application concern:

```text
Application/
└─ Deleting/
   ├─ IBookmarkDeleteService.cs
   ├─ BookmarkDeleteService.cs
   ├─ BookmarkDeleteError.cs
   ├─ BookmarkDeleteException.cs
   ├─ BookmarkDeleteResult.cs
   └─ BookmarkBatchDeleteResult.cs
```

The service owns:

- active-document membership validation;
- protected-root validation;
- subtree counting;
- exact parent/index capture;
- single delete;
- batch bookmark delete.

Batch movement remains part of the movement concern, extending `IBookmarkMoveService` with an atomic/group-oriented operation rather than duplicating detach/insert rules in WPF.

WPF code-behind may translate selection and confirmation gestures, but it must never directly mutate `BookmarkFolder.Children`.

---

## 5. Domain count semantics

V0.5 add operations increment `BookmarkDocument.UrlCount` / `FolderCount`. V0.7 must add the symmetric removal path.

Add a narrow internal document primitive such as:

```csharp
internal void RecordRemovedSubtree(
    int removedUrlCount,
    int removedFolderCount)
```

Rules:

- counts may never become negative;
- count validation occurs before committed mutation where possible;
- deleting one bookmark decrements URL count by one;
- deleting a folder decrements folder count by the folder plus all descendant folders and decrements URL count by all descendant bookmarks;
- `TotalNodeCount` remains derived from the two counters;
- `_maximumNodeId` never moves backwards;
- deleted GUIDs remain reserved in the document's known-GUID set so later additions do not intentionally reuse identity.

## 6. Delete invariants

Every delete must satisfy:

### 6.1 Protected roots

Permanent roots cannot be deleted.

### 6.2 Membership

The deleted node must belong to the active `BookmarkDocument`.

A detached, stale, or foreign-document node is rejected.

### 6.3 Exact detach

After successful deletion:

- the old parent no longer contains the deleted node;
- the deleted root node has `Parent == null`;
- descendants remain internally connected to the deleted folder subtree;
- unrelated nodes retain identity and order.

### 6.4 Count correctness

Document counts decrease by exactly the deleted subtree size.

### 6.5 Identity preservation of survivors

Deletion never recreates unaffected bookmark/folder objects.

### 6.6 No source-file mutation

Delete means **remove from the loaded in-memory graph only**.

V0.7 must not call file delete/write/replace APIs against the Chrome source path.

---

## 7. Batch-delete semantics

Batch bookmark deletion is all-or-nothing by contract.

Before mutation:

1. materialize the requested bookmark references;
2. reject null/foreign/detached nodes;
3. deduplicate by reference;
4. capture every source parent and source mixed-child index;
5. group deletions by parent;
6. validate document count impact.

Mutation removes each parent's selected children in descending mixed-child-index order so earlier indexes do not shift.

The returned result records enough information for V0.8 Undo / Redo design:

- removed bookmark reference;
- original parent;
- original mixed-child index.

V0.7 does not implement Undo / Redo itself.

---

## 8. Batch-move semantics

Batch bookmark Move to... uses the V0.6 hierarchy/membership rules.

The caller passes an explicitly ordered bookmark list captured from `DisplayedBookmarks`.

The operation:

1. validates target and all selected bookmarks;
2. captures source parent/index snapshots;
3. removes selected bookmarks safely;
4. appends them to the target in supplied order;
5. preserves bookmark identity and metadata;
6. leaves document counts unchanged;
7. reports `Changed=false` when the requested group is already in the same effective end-state;
8. restores original structure if an unexpected mutation-stage exception occurs.

Search-result order is allowed to define batch group order because it is deterministic display order captured before mutation; positional Drag & Drop inside search results remains prohibited as established by V0.6.

## 9. Selection model

`SelectedBookmark` remains as the primary/active bookmark for compatibility with rename/edit URL and V0.6 single-node commands.

Add a batch selection surface, for example:

```csharp
IReadOnlyList<BookmarkUrl> SelectedBookmarks
int SelectedBookmarkCount
bool HasMultipleSelectedBookmarks
```

Because WPF `ListView.SelectedItems` is not directly bindable, code-behind may forward `SelectionChanged` to one ViewModel method that accepts the selected bookmark references.

Selection must be cleared or reconciled after:

- folder navigation;
- search query/scope changes;
- delete;
- move;
- reload;
- load failure/cancellation.

No stale selected reference may enable a destructive command.

---

## 10. Search/index behavior

### Delete

Delete changes index membership, so successful single/batch deletion must rebuild the in-memory search index from the mutated document before active search is rerun.

Deleted bookmarks must never remain in search results.

### Move

Batch move does not change bookmark searchable text, so it follows V0.6 semantics:

- no search-index rebuild;
- active search is rerun/re-scoped from the existing index;
- current-folder scope reflects new parents.

---

## 11. Confirmation UX

Destructive commands use explicit confirmation with safe default cancellation.

Bookmark confirmation includes:

- single bookmark name when one is selected;
- selected count for batch delete.

Folder confirmation includes:

- folder name;
- descendant bookmark count;
- descendant folder count;
- clear wording that the entire subtree will be removed from the current in-memory document.

The dialog must also state that V0.7 has no Save/write-back path, so these changes affect only the loaded session.

Cancel performs no mutation and does not mark the document dirty.

---

## 12. Dirty-state behavior

Successful delete or batch operation marks the document `LoadedDirty`.

No-op/cancel/invalid operations do not mark clean documents dirty.

Existing dirty-document Discard / Cancel protection remains unchanged.

Because there is still no Save:

- Discard reload/close loses V0.7 deletions and batch moves;
- source Chrome `Bookmarks` remains unchanged.

---

## 13. Keyboard/context-menu behavior

Bookmark list:

- Delete -> delete selected bookmark(s);
- Ctrl+A -> select all displayed bookmarks;
- context menu Delete -> batch-aware delete;
- context menu Move to... -> batch-aware when multiple bookmarks are selected;
- existing rename/edit URL operate only on the primary bookmark and are disabled when multi-selection would make the target ambiguous.

Folder tree:

- Delete -> delete selected ordinary folder;
- context menu Delete -> delete selected ordinary folder;
- root delete disabled.

V0.6 Drag & Drop remains a single-node gesture in V0.7; dragging a multi-selection does not implicitly become group drag unless a later milestone explicitly designs it.

---

## 14. Performance and scale

The owner has a real library of roughly 209k URLs and 3.4k folders.

Normal V0.7 CI should include synthetic tests for:

- many bookmarks across many parents;
- batch deletion;
- large folder-subtree deletion;
- batch move;
- exact count verification;
- parent/order coherence;
- search rebuild after deletion.

Correctness must not depend on fragile wall-clock thresholds.

---

## 15. Safety boundary

V0.7 remains strictly in-memory.

Forbidden production behavior includes:

- `File.Delete` against the source;
- `File.WriteAllText`;
- `File.WriteAllBytes`;
- `File.Replace`;
- serialization back to `SourcePath`;
- backup/atomic-replace logic;
- Chrome process handling.

Safe Chrome write-back remains V0.9.

---

## 16. Explicitly deferred

V0.7 does not implement:

- Save;
- source-file write-back;
- folder-tree multi-selection;
- batch Drag & Drop;
- Undo / Redo;
- recycle bin/trash persistence;
- backup/checksum regeneration;
- Chrome process coordination.

Undo / Redo remains V0.8. Safe Chrome Write remains V0.9.
