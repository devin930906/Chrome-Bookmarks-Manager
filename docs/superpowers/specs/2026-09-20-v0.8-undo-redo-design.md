# V0.8 Undo / Redo Design

> Status: implementation design for the V0.8 reversible in-memory mutation milestone.

## Goal

Add deterministic session-local Undo / Redo for the editing, movement, and deletion operations delivered by V0.5–V0.7 without adding any Chrome source-file write path.

V0.8 must make the application behave like a normal desktop bookmark manager: a successful mutation creates one reversible history entry, Undo walks backward one logical operation at a time, Redo reapplies the same operation, and a new mutation after Undo discards the obsolete redo branch.

## Baseline

V0.7 completed on `main` at `a7d2c27213b76cc0a295c4e7f46e09987f71878c`.

Existing mutation families:

- V0.5: add bookmark, add folder, rename bookmark/folder, edit URL;
- V0.6: bookmark/folder Move to..., bookmark/folder Drag & Drop reorder/move;
- V0.7: single bookmark delete, recursive ordinary-folder delete, batch bookmark delete, batch bookmark Move to....

## Safety boundary

V0.8 remains strictly in-memory.

Forbidden for V0.8 production code:

- Save or write-back to the source Chrome `Bookmarks` file;
- `File.Delete`, source overwrite, replace, backup, checksum regeneration, or Chrome process coordination;
- serialization-based whole-document snapshots as the normal undo mechanism;
- committing or uploading the owner's private bookmark data.

Undo / Redo must operate on the already loaded object graph and preserve existing node identity, IDs, GUIDs, timestamps, metadata, unknown properties, and child order unless the original operation intentionally changed order.

## History model

Use a linear history with a cursor instead of independent ad-hoc booleans.

Conceptually:

```text
entry 0 | entry 1 | entry 2 | entry 3
                  ^
                cursor
```

- entries before the cursor are applied;
- entries at/after the cursor are redo candidates;
- Undo reverts entry `cursor - 1` and decrements the cursor only after a successful revert;
- Redo reapplies entry `cursor` and increments the cursor only after a successful replay;
- recording a new mutation while the cursor is not at the end removes the redo tail first;
- failed/no-op/cancelled operations do not create history entries;
- loading/reloading/discarding a document clears history.

The history manager owns:

- `CanUndo`;
- `CanRedo`;
- current position;
- clean position;
- Undo/Redo descriptions;
- branch truncation;
- bounded history behavior;
- clean-state reachability.

## Dirty-state rule

V0.8 replaces one-way `MarkDirty()` semantics with history-position semantics.

A document is clean when the current history position equals the clean position.

This is mandatory so that:

1. load document -> clean;
2. rename -> dirty;
3. Undo rename -> clean;
4. Redo rename -> dirty.

If bounded-history trimming removes the recorded clean position, the clean state becomes unreachable for that session and the document remains dirty until reload/discard or a future save milestone establishes a new baseline.

## History capacity

Default history capacity: **200 logical operations**.

Reasons:

- avoids unbounded growth during long sessions;
- each entry stores references and compact mutation snapshots rather than a full document clone;
- large deleted subtrees remain referenced only as needed to support Undo;
- 200 operations is sufficient for normal interactive use while keeping behavior predictable.

Capacity behavior must be tested explicitly.

## History entry contract

Each logical mutation becomes one history entry exposing:

- human-readable description;
- projection refresh impact;
- `Undo(BookmarkDocument)`;
- `Redo(BookmarkDocument)`.

Projection refresh impact distinguishes:

- search-relevant changes: add, delete, rename, URL edit;
- structure-only movement: Move to... / Drag & Drop / batch move.

Search-relevant Undo/Redo rebuilds the search index and reruns active search. Pure movement reuses the existing search index and only refreshes browser/search projections.

## Reversible operation rules

### Add bookmark / folder

Record:

- exact node reference;
- parent reference;
- insertion index.

Undo:

- detach the same node;
- decrement document counts.

Redo:

- reinsert the same node at the recorded index;
- restore counts.

No new ID/GUID/timestamp is allocated on Redo.

### Rename bookmark / folder

Record:

- node reference;
- previous name;
- new sanitized name.

Undo/Redo set the stored values on the same node.

### Edit URL

Record:

- bookmark reference;
- previous URL;
- new URL.

Undo/Redo set stored values on the same bookmark.

### Single move / reorder

Record:

- node reference;
- source parent/index;
- target parent/index.

Undo restores source placement exactly.
Redo restores target placement exactly.

### Batch bookmark move

Record the ordered set of moved bookmark references and each original source parent/index plus the final target indexes.

Undo and Redo must be atomic and preserve group order.

### Single delete / recursive folder delete

Reuse the V0.7 delete snapshot:

- detached node/subtree reference;
- source parent/index;
- removed URL/folder counts.

Undo restores the detached subtree and counts.
Redo removes the same subtree again.

### Batch bookmark delete

Reuse per-item V0.7 snapshots.

Undo restores bookmarks to their original parents/indexes.
Redo removes them again.
Both directions must be atomic and exact.

## Failure semantics

Undo/Redo is transactional at the history cursor level:

- the cursor changes only after the entry operation succeeds;
- if an entry detects a stale/invalid graph state, it throws and the cursor remains unchanged;
- compound entries roll back partial work before rethrowing;
- a failed Undo/Redo must not silently mark the document clean or advance history.

## ViewModel integration

MainViewModel adds:

- `CanUndo`;
- `CanRedo`;
- `UndoDescription`;
- `RedoDescription`;
- `UndoAsync()`;
- `RedoAsync()`.

Every successful V0.5–V0.7 mutation records exactly one history entry.

After Undo/Redo:

- browser lists/folder tree are coherent;
- active search remains coherent;
- selection falls back safely if a node disappears;
- restored nodes remain the same object instances;
- dirty state is recomputed from history position.

## WPF UX

Required V0.8 controls:

- Undo command: `Ctrl+Z`;
- Redo command: `Ctrl+Y`;
- alternate Redo command: `Ctrl+Shift+Z`;
- visible Undo and Redo controls;
- disabled state when unavailable;
- command text/tooltips may include the pending operation description.

Undo/Redo must not interfere with text-entry controls' normal local editing behavior when a text box owns keyboard focus.

## Scale and privacy

Normal CI adds an UndoRedoScale category using synthetic reserved-domain data.

Minimum scale coverage:

- many sequential rename/URL history entries;
- large batch delete -> Undo -> Redo;
- recursive large-folder delete -> Undo -> Redo;
- batch move -> Undo -> Redo;
- branch truncation after many operations.

Large-scale timing is diagnostic only, not a correctness threshold.

## Acceptance boundary

Windows 10 owner acceptance uses the private Chrome Bookmarks file but never commits or uploads it.

Acceptance must prove:

- all supported forward mutations can be undone/redone;
- multiple-step Undo/Redo ordering is correct;
- redo branch disappears after a new edit;
- Undo back to baseline returns the app to clean state;
- Dirty Discard/Cancel remains correct;
- V0.7 delete/batch and V0.6 Drag & Drop regressions remain correct;
- source SHA-256, byte length, and LastWriteTimeUtc remain unchanged.
