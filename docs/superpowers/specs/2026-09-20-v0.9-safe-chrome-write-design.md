# V0.9 Safe Chrome Write Design

> **Status:** implementation design for the V0.9 persistence milestone  
> **Date:** 2026-09-20  
> **Baseline:** V0.8 completed on `main` at `3d0ff6fe06e9acc230de1f6fd04e13973fb59332`  
> **Branch:** `feature/v0.9-safe-chrome-write`

## Goal

Add a data-safety-first persistence path that can serialize the current in-memory bookmark graph, reproduce Chrome-compatible bookmark checksums, validate the generated file, create a verified backup, and replace the loaded clear-text `Bookmarks` file without exposing the user to a best-effort or partially written save.

V0.9 is the first milestone allowed to modify a Chrome bookmark source file. Therefore a save is considered successful only when every required precondition, write, validation, backup, replace, and post-write verification stage succeeds.

## Safety boundary

V0.9 must preserve these invariants:

- no write occurs merely because a document is loaded or edited;
- Save is explicit;
- the loaded source path is the only direct-save destination;
- a dirty in-memory document is never written if the source file changed externally since the accepted baseline;
- Chrome must not be running when direct replacement is attempted;
- the new content is first written to a same-directory temporary file;
- the temporary file must pass the project's own reader/validation before the source is touched;
- a byte-for-byte backup of the current source must exist and be verified before replacement;
- the final replacement is same-volume and atomic at the filesystem-operation level;
- the replacement result must be reopened and validated;
- failure at any stage must not be reported as success;
- the verified backup is retained after a successful write;
- private bookmark data, backup contents, generated output, and local test-profile data never enter GitHub or CI.

V0.9 does not claim crash-proof durability beyond what the Windows/.NET filesystem primitives can guarantee. Atomic replacement protects against partial destination replacement, but cannot honestly guarantee survival of every power-loss/storage-controller scenario.

## Current Chromium compatibility audit

Audit date: **2026-09-20**.

Current Chromium source was rechecked before implementation planning:

- `BookmarkCodec` still defines both `checksum` and `checksum_sha256`, maintains MD5 and SHA-256 hashers, and computes both values.
- Checksum input is semantic bookmark data, not the JSON byte stream.
- URL-node checksum sequence is: node ID, UTF-16 title bytes, literal `url`, UTF-8 URL.
- Folder-node checksum sequence is: node ID, UTF-16 title bytes, literal `folder`.
- Traversal is root order `bookmark_bar`, `other`, `synced`, with each subtree traversed in child order.
- Current Chromium bookmark storage uses its codec plus `ImportantFileWriter`-style guarded persistence.
- Chromium currently contains clear-text/encrypted bookmark storage feature paths. V0.9 supports only the already-loaded clear-text version-1 `Bookmarks` document; encrypted bookmark storage is out of scope.

Reference source:
- https://chromium.googlesource.com/chromium/src/+/HEAD/components/bookmarks/browser/bookmark_codec.h
- https://chromium.googlesource.com/chromium/src/+/HEAD/components/bookmarks/browser/bookmark_codec.cc
- https://chromium.googlesource.com/chromium/src/+/HEAD/components/bookmarks/browser/bookmark_storage.h
- https://chromium.googlesource.com/chromium/src/+/HEAD/components/bookmarks/browser/bookmark_storage.cc

The audit is evidence for implementation, not a permanent assumption. The compatibility gate must be repeated if Chromium materially changes bookmark persistence before release.

## Checksum design

Create an isolated `ChromeBookmarksChecksum` component.

It must:

- compute the legacy MD5 checksum required by current Chrome compatibility;
- compute SHA-256 from the same logical input stream;
- produce lowercase hexadecimal strings;
- process roots in Chrome order;
- process descendants in exact stored child order;
- feed IDs as UTF-8 bytes;
- feed titles as UTF-16 little-endian code-unit bytes on Windows-compatible semantics;
- feed node type literals and URL bytes as UTF-8;
- exclude GUIDs, timestamps, `meta_info`, extension data, and JSON formatting from checksum input.

The checksum component must not perform filesystem I/O.

Writer output will regenerate both `checksum` and `checksum_sha256` from the current graph. Acceptance against a real disposable Chrome test profile is mandatory before production-profile overwrite is allowed.

## Writer design

Add a dedicated Chrome writer/codec boundary rather than serializing domain objects implicitly.

Conceptual flow:

```text
BookmarkDocument
  ↓ validate graph
ChromeBookmarksWriter
  ↓ compute checksums
Utf8JsonWriter
  ↓
temporary Bookmarks file
```

Required preservation:

- version;
- root identities and root names;
- node IDs and GUIDs;
- child ordering;
- URL/name values;
- raw Chrome timestamp strings;
- `meta_info` as currently retained by the reader;
- root/node/top-level unknown extension properties;
- supported optional properties;
- exact logical URL/folder counts.

Known writer-owned properties must win over extension-data collisions. Extension data must never be able to emit a second reserved property such as `id`, `type`, `roots`, or `checksum`.

The writer must use UTF-8 JSON and deterministic property handling. Byte-for-byte equality with Chrome's formatting is not required; semantic and Chrome compatibility are required.

## Round-trip contract

Every synthetic writer test must support:

```text
input
 ↓ reader
BookmarkDocument
 ↓ writer
output
 ↓ reader
BookmarkDocument
```

Verify:

- same node count;
- same three-root hierarchy;
- same node IDs/GUIDs;
- same names and URLs;
- same ordered children;
- same date strings;
- same `meta_info`;
- same extension fields;
- regenerated checksum values match the graph;
- output reader validation succeeds.

A logical comparer/fingerprint may be introduced for tests and pre-replace validation, but must not duplicate the complete document in production memory unless justified by measurement.

## Source baseline / optimistic concurrency

Loading a source file must establish a persistence baseline containing at least:

- normalized full path;
- SHA-256 of source bytes;
- byte length;
- last-write UTC timestamp.

Immediately before Save replaces the source, recalculate and compare the baseline.

If any baseline component differs, abort with an explicit **source changed externally** error. Do not merge automatically and do not overwrite.

After a successful verified Save:

- capture a new baseline from the final file;
- mark the current history position clean;
- keep Undo/Redo history available;
- future Undo makes the document dirty again;
- Redo back to the saved checkpoint returns it to clean.

## Chrome process protection

Direct source replacement requires Chrome to be closed.

V0.9 uses a deliberately conservative rule:

- if any `chrome.exe` process is detected, direct Save is blocked;
- the check occurs before the expensive persistence transaction and again immediately before replacement;
- inability to perform the process check is a safety failure, not permission to continue.

This can be refined later to profile-specific process coordination only if it can be verified reliably.

## Save transaction

The production save orchestration is:

```text
1. Validate editable loaded document
2. Validate supported clear-text source
3. Confirm Chrome is not running
4. Verify source still matches load/save baseline
5. Compute new Chrome checksums
6. Write complete output to unique temp file in source directory
7. Flush/close temp file
8. Re-open temp with ChromeBookmarksReader
9. Verify round-trip logical equivalence/checksums
10. Create unique timestamped application backup of current source
11. Verify backup SHA-256 and length equal current source
12. Re-check Chrome process state
13. Re-check source baseline
14. Atomically replace source with temp
15. Re-open final source
16. Validate final document and logical equivalence
17. Capture new source baseline
18. Mark history checkpoint clean
19. Report success
```

Do not use Chrome's own `Bookmarks.bak` filename for the application's safety backup. Use an application-identifiable unique backup name so Chrome's own recovery behavior is not overwritten or confused.

Example pattern:

```text
Bookmarks.ChromeBookmarksManager.20260920-215100.000.bak
```

Collision handling must remain deterministic and must never overwrite an existing backup.

## Failure and recovery semantics

Before replacement:

- any failure leaves the original source untouched;
- temporary files are cleaned when safe;
- a created verified backup may be retained.

During replacement:

- failure must surface as a typed save error;
- the original must not be intentionally deleted first;
- no delete-then-move strategy is allowed.

After replacement:

- if final validation fails, report a critical save failure and preserve the verified backup;
- automated rollback may be added only if its own operation can be made safer than stopping and preserving evidence;
- V0.9 initially prefers explicit recovery from the verified backup over cascading replacement attempts after an unexpected post-replace validation failure.

The UI must display the backup path for failures where recovery may be required, without logging bookmark contents.

## Typed errors

Create a save error model that distinguishes at least:

- no loaded source;
- unsupported source/version;
- Chrome running;
- process-check failure;
- source changed externally;
- source missing;
- access denied;
- serialization/validation failure;
- temp-file write/flush failure;
- backup creation failure;
- backup verification failure;
- atomic replacement failure;
- post-write validation failure;
- recovery required;
- cancellation before replacement.

Errors shown to the user must be actionable.

## Cancellation boundary

Cancellation is allowed during expensive pre-replace work such as checksum/write/validation.

Once the transaction enters the final backup/recheck/replace critical section, cancellation must not interrupt the operation between safety-critical filesystem steps. A cancellation request received after that boundary can be observed after the transaction reaches a coherent state.

## ViewModel integration

`MainViewModel` gains persistence dependencies rather than implementing filesystem writes itself.

Expose at least:

- `CanSave`;
- `SaveAsync()`;
- save-state status text;
- typed failure handling;
- source baseline lifecycle.

State transitions:

```text
LoadedDirty → Saving → LoadedClean
LoadedDirty → Saving → SaveFailed
SaveFailed → retryable LoadedDirty behavior
```

The exact state transition after failure must keep the active document usable and dirty; `SaveFailed` must not make the user lose the loaded graph.

On success, call the V0.8 history manager's `MarkClean()`.

## WPF UX

Required:

- visible Save control;
- `Ctrl+S`;
- Save disabled when there is no document, document is clean, load/save is in progress, or direct-save preconditions are not satisfied;
- clear warning that Save writes the loaded Chrome `Bookmarks` file;
- actionable Chrome-running message;
- progress/status stages without fabricated percentages;
- success status includes that backup + verification succeeded;
- failure status never claims the source is safe unless the actual transaction stage supports that claim.

The dirty-close/reload dialogs must evolve from the V0.5 Discard/Cancel-only model. At minimum, while dirty they must not imply Save exists if the save preconditions are currently blocked. Final UX can offer Save / Discard / Cancel only after Save has passed its own integration tests.

## Test-profile gate

Before touching the owner's production Chrome profile, create/use a disposable Chrome test profile containing only synthetic/non-private test bookmarks.

Required manual compatibility sequence:

1. Chrome fully closed.
2. Capture test-profile `Bookmarks` baseline.
3. Load with the app.
4. Perform representative add/edit/move/delete operations.
5. Save through V0.9.
6. Confirm backup exists and matches the pre-save source.
7. Start Chrome with the test profile.
8. Confirm all expected bookmark changes appear.
9. Make a bookmark change inside Chrome.
10. Close Chrome cleanly.
11. Re-open the resulting file in the app.
12. Verify structure, IDs/GUIDs, checksums, metadata handling, and no corruption.
13. Repeat with Unicode/Chinese titles and nested folders.

Only a PASS unlocks production-profile owner acceptance.

## Production owner acceptance

Production acceptance requires an independent external copy of the real `Bookmarks` file made before testing.

Then verify on Windows 10:

- real file loads;
- representative operations save;
- application backup is created and hash-verified;
- Chrome reads the result;
- Chrome can subsequently save its own changes;
- app can reload Chrome's result;
- Undo/Redo dirty-state behavior around a saved checkpoint is correct;
- stale-source detection blocks overwrite;
- Chrome-running detection blocks overwrite;
- replacement-failure test is performed only on synthetic/test-profile data, never by deliberately faulting the production file;
- no private bookmark content is committed/uploaded.

## CI and privacy

Normal CI uses only synthetic fixtures.

Add V0.9 gates for:

- checksum vectors;
- writer round-trip;
- extension data and `meta_info` preservation;
- checksum regeneration;
- source-baseline conflict;
- verified backup;
- atomic replacement;
- failure injection;
- post-write reload;
- Save state/history checkpoint;
- WPF Save UI contract;
- persistence scale using generated data;
- repository privacy checks;
- full regression;
- single-file publish and smoke test.

Real Chrome compatibility remains a Windows owner/test-profile acceptance gate and is not simulated as proof by CI.

## Non-goals

V0.9 does not add:

- encrypted Chrome bookmark-file support;
- concurrent merge with a running Chrome instance;
- Chrome Sync protocol manipulation;
- cloud sync;
- cross-platform write support;
- arbitrary JSON repair;
- automatic deletion/rotation of safety backups;
- production write without explicit Save;
- silent overwrite after an external source change.

## Release gate

V0.9 is complete only when all are true:

- current Chromium format/checksum audit recorded;
- checksum implementation matches Chromium vectors;
- writer round-trip passes;
- unknown fields and `meta_info` survive;
- Chrome timestamps/IDs/GUIDs survive;
- new-node ID/GUID behavior is reverified;
- temp write and validation pass;
- baseline conflict detection passes;
- Chrome-process protection passes;
- backup and backup verification pass;
- atomic replace and replacement-failure tests pass;
- post-write reload passes;
- Save/history clean-checkpoint semantics pass;
- Windows CI is green;
- disposable Chrome test profile passes;
- external production backup exists;
- Windows 10 production owner acceptance passes;
- final whole-branch review has no Critical/Important data-safety defects;
- PR is merged and post-merge `main` is green.

Until every critical item above passes, V0.9 remains pre-release and production-profile overwrite is not considered approved.
