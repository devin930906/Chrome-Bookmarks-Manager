## 1. Purpose

V1.0 converts the completed V0.1–V0.9 implementation into the first stable personal-use release.

V1.0 is not a feature-expansion milestone. The existing browse, search, edit, move, drag/drop, delete, batch, Undo/Redo, and Safe Chrome Write paths are already implemented. This milestone formalizes version identity, removes development-stage residue from the production UI, adds a durable release pipeline, runs final regression and scale gates, completes Windows 10 owner acceptance, and publishes a reproducible GitHub Release.

The intended outcome is:

```text
Chrome Bookmarks Manager 1.0.0
= stable daily-use personal release
= existing functionality + release hardening
= no new bookmark-management features
```

## 2. Scope freeze

### 2.1 In scope

V1.0 may change only what is required to produce a coherent stable release:

- explicit product/file/assembly version metadata for 1.0.0;
- one authoritative version source;
- runtime-visible version identification;
- removal of stale V0.x user-facing wording;
- removal of non-functional production menu placeholders;
- V1.0 release-readiness verification;
- a dedicated GitHub Release workflow;
- release-tag/project-version consistency checks;
- SHA-256 generation and verification;
- release-scale synthetic measurements;
- final Windows 10 owner acceptance;
- README and roadmap stabilization;
- final code review, merge, tag, release, and post-release verification.

### 2.2 Out of scope

The following are explicitly deferred beyond V1.0:

- duplicate URL detection;
- import/export;
- Chrome bookmark HTML support;
- dead-link checking;
- automatic classification;
- settings UI;
- About dialog;
- portable mode;
- SQLite or another new primary store;
- favicon downloading;
- new search capabilities;
- new persisted sorting features;
- large UI redesign;
- Fluent UI/theme work;
- cloud/mobile/macOS/Linux support;
- browser extension functionality.

If a non-blocking new idea appears while V1.0 is being implemented, it belongs in a later milestone rather than expanding V1.0.

### 4.1 Stable version

The first stable release is:

```text

Assembly version: 1.0.0.0
Git tag:          v1.0.0
```

### 4.2 Single source of truth

Version values must not be maintained independently across unrelated files.

The project will establish one authoritative project version value from which the runtime and build metadata derive. Release automation must compare the release tag to that authoritative version before publishing.

### 4.3 Runtime identification

The main application must make the running version identifiable without introducing a new About subsystem.

Preferred V1.0 title:

```text
Chrome Bookmarks Manager 1.0.0
```

Future patch/minor releases then become immediately distinguishable when multiple EXEs exist.

## 5. Production UI cleanup

V1.0 removes development-stage residue but does not redesign the application.

### 5.1 Stale V0.x wording

User-facing text that describes obsolete milestone behavior must be updated.

Known example:

```text
Open a Chrome Bookmarks file. V0.6 edits and moves remain in memory.
```

This is no longer true because V0.9 introduced explicit Safe Save.

The replacement wording must preserve the current safety model, for example:

```text
Open a Chrome Bookmarks file for browsing and editing.
Changes are written only when you explicitly choose Save.
```

Historical V0.x references in engineering documentation remain intact because they are valid development evidence.

### 5.2 Non-functional menu placeholders

Production UI must not imply unfinished features.

Current non-functional placeholders such as disabled/empty View, Tools, and disabled Exit entries should be removed rather than filled with new features solely to make the menu look complete.

The retained menu surface should contain only real commands.

### 5.3 No visual redesign

V1.0 retains the existing high-density Windows management layout. It does not introduce themes, dashboards, animation systems, ribbons, settings surfaces, or decorative redesign work.

Priority remains:

```text
Data correctness
> Data safety
> Tests
> Performance
> Usability
> Visual polish
```

## 6. Safe Save invariants

V1.0 must preserve the V0.9 persistence safety boundary.

The production save path remains:

```text
In-memory document
  ↓
Pre-save validation
  ↓
Chrome-running check
  ↓
Accepted source baseline check
  ↓
Write unique same-directory temporary file
  ↓
Re-open and validate temporary file
  ↓
Create application-owned backup
  ↓
Verify backup
  ↓
Final source recheck
  ↓
Atomic File.Replace
  ↓
Re-open final source
  ↓
Post-write validation
  ↓
Clean saved checkpoint
```

V1.0 must not introduce:

- automatic save;
- close-time silent write;
- Chrome-running force overwrite;
- delete-then-move replacement;
- skipped backup verification;
- skipped checksum handling;
- skipped post-write validation.

A stable release is not permission to weaken safety.

---

## 7. Dirty state and history integration

The existing document states remain authoritative:

- `NoDocument`;
- `Loading`;
- `LoadedClean`;
- `LoadedDirty`;
- `Saving`;
- `SaveFailed`.

The saved checkpoint semantics remain:

```text
Edit → Dirty
Save → Clean
Undo away from saved checkpoint → Dirty
Redo back to saved checkpoint → Clean
```

V1.0 may repair inconsistent user-facing state text if found, but must not redesign the history model.

## 9. CI and release workflow separation

### 9.1 Development CI

Existing workflow:

```text
.github/workflows/build-windows.yml
```

Purpose:

- push/PR/main validation;
- privacy gate;
- build;
- full test suite;
- named scale gates;
- UI/static safety gates;
- Windows x64 publish;
- single-file verification;
- smoke test;
- short-lived CI artifact.

Its current short artifact retention remains appropriate for development output.

### 9.2 Formal release workflow

V1.0 adds:

```text
.github/workflows/release-windows.yml
```

This workflow is dedicated to formal releases rather than ordinary development artifacts.

It must:

1. resolve the tagged commit;
2. validate tag format;
3. verify tag version equals project version;
4. restore;
5. build Release;
6. run repository-safety verification;
7. run required tests and release gates;
8. publish `win-x64` self-contained single-file output;
9. verify the final EXE contract;
10. verify EXE version metadata;
11. generate SHA-256;
12. create/publish the GitHub Release;
13. upload only approved release assets.

The formal Release must be reconstructed and validated from the tagged source. It must not simply promote an old short-lived Actions artifact.

Owner-acceptance scripts may remain tracked in the repository as engineering evidence, but they are not part of the stable user download.

## 11. SHA-256 integrity contract

The release pipeline generates a SHA-256 checksum for the final EXE.

The checksum must correspond exactly to the published `ChromeBookmarksManager.exe`.

A user must be able to verify it with a standard Windows command such as:

```powershell
Get-FileHash .\ChromeBookmarksManager.exe -Algorithm SHA256
```

Release verification must ensure the recorded checksum matches the final asset bytes.

## 13. V1.0 release-scale measurements

Before stable release, larger synthetic measurements are run explicitly.

The release-readiness process should cover approximately:

- Reader: 250,000 URLs;
- Browser: 250,000 URLs;
- Search: 250,000 URLs;
- Move: 250,000 URLs plus a larger synthetic folder workload;
- Delete/Batch: 250,000 URLs plus a larger synthetic folder workload;
- Write: 250,000 URLs.

Observed time and memory data are diagnostic evidence. V1.0 must not invent arbitrary performance thresholds without an empirical basis.

Correctness criteria remain primary:

- no corruption;
- expected counts;
- expected identities/order;
- expected search/mutation behavior;
- successful write/read round trip;
- no release-blocking exceptions.

## 15. Windows 10 owner acceptance

CI is necessary but insufficient because the actual daily-use workload is the owner's real Chrome library.

Final V1.0 owner acceptance is performed on Windows 10 against the real private production library, approximately:

- 119 MB;
- 209k URL nodes;
- 3.4k folders.

Private bookmark content must never be committed or uploaded.

### 15.1 Launch and load

Verify:

- final release candidate EXE launches without a separate runtime install;
- visible runtime version is 1.0.0;
- the real Bookmarks file loads;
- observed URL/folder counts are coherent;
- three roots render correctly;
- browsing remains usable.

Observed load time is recorded as diagnostic evidence rather than a hard SLA.

### 15.2 Browse/search path

Verify:

- folder navigation;
- large bookmark-list scrolling;
- Name search;
- URL/domain-text search;
- Chinese / Unicode search;
- All bookmarks scope;
- Current folder scope;
- search clearing;
- search-result navigation.

### 15.3 Mutation path

Use narrowly controlled test nodes and verify:

- add bookmark;
- add folder;
- rename bookmark;
- rename folder;
- edit URL;
- move bookmark;
- move folder;
- Drag & Drop;
- reorder;
- batch select;
- batch move;
- delete;
- Undo;
- Redo.

### 15.4 Safe Save

With Chrome fully closed:

1. capture the source baseline;
2. make controlled test changes;
3. invoke Save;
4. verify Save succeeds;
5. verify Dirty becomes Clean;
6. verify application backup exists;
7. verify backup SHA-256/length match the exact pre-save source;
8. verify final source parses and validates;
9. reopen the final source successfully.

### 15.5 Chrome compatibility

After application Save:

1. close Chrome Bookmarks Manager;
2. launch normal Chrome;
3. confirm there is no corruption/recovery warning;
4. confirm the edited bookmark structure is visible;
5. close Chrome normally so Chrome may rewrite the file;
6. reopen the Chrome-rewritten file in V1.0;
7. verify it remains readable and coherent.

### 15.6 Chrome-running protection

With Chrome running, an attempted direct Save to the loaded Chrome source must be blocked and must not overwrite the source.

After Chrome is fully closed, Save should again be permitted when all other safety conditions are satisfied.

### 15.7 Stale-source conflict

Conflict testing must use a disposable/synthetic copy rather than intentionally damaging the production source.

After the application accepts a baseline, externally modify the source and verify the next Save is blocked.

### 15.8 Saved checkpoint

Verify:

```text
Edit → Save → Clean → Undo → Dirty → Redo → Clean
```

## 16. Release-blocking defects

A defect blocks V1.0 when it risks correctness, data safety, or the core daily-use path.

Examples:

- Save may overwrite externally changed source data;
- backup is wrong or unverifiable;
- checksum handling is incorrect;
- Chrome rejects or recovers the written file;
- real large Bookmarks loading fails;
- Undo/Redo produces an incorrect saved checkpoint;
- movement/deletion corrupts hierarchy/order;
- application crashes in a normal core flow;
- single-file distribution is broken;
- tagged release/version identity is inconsistent.

A blocking defect must be fixed and relevant gates rerun before release.

Minor visual/text issues that do not affect correctness, safety, or the daily-use path may be recorded for a later patch/minor release rather than expanding V1.0 indefinitely.

## 18. TDD and implementation discipline

Although V1.0 is mostly release hardening, test-first development remains required for behavior and release-contract changes.

Typical pattern:

```text
RED
↓
GREEN
↓
REFACTOR
```

Examples:

- version-contract test fails before 1.0.0 metadata exists;
- release-asset contract fails before the workflow produces the required shape;
- stale production UI contract fails before obsolete wording/placeholders are removed.

Implementation tasks should remain small, independently verifiable, and commit frequently.
